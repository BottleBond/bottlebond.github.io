### System Design Exercise

**Problem Statement**: Design a CI system to test ML inference software across multiple hardware types and models, ensuring deterministic results and tracking performance over time  

**Key Requirements**:

- Test across matrix of hardware types (GPUs, inference cards, even Raspberry Pi)
- Ensure deterministic output across different hardware (Jensen's core product feature)
- Run as part of CI pipeline on every commit
- Track performance trends over time to detect regressions
- Alert developers if builds break on specific hardware types

### Proposed Solution Architecture

**Development Workflow**:

- Pre-commit hooks for basic validation (style, large files, secrets) to catch issues before submission
- Standardized pre-commit tooling across projects
- GitHub Actions trigger on commit

**Build Distribution**:

- Treat build artifacts as Docker containers (using Bazel for optimization)
- Use Docker layer caching to minimize distribution of unchanged components
- Stage testing based on hardware availability - run on plentiful resources first, then cascade to scarce resources

**Execution Infrastructure**:

- Deploy on Kubernetes cluster with nodes labeled by hardware attributes
- Use Helm charts to define job matrix and manage deployments
- Implement FIFO queuing (suggested Red Panda or similar) for scarce resources like H100 GPUs
- Queue service manages job scheduling based on hardware availability

**Data Collection & Monitoring**:

- Collect firmware data, process details, system state at runtime
- For anomalies: dump memory state, open file tables, filesystem health
- Stream metrics data passively to avoid impacting build performance
- Store detailed forensic data in compressed format in object storage (S3) for long-term retention
- Primary focus on telemetry showing build success/failure and performance trends

### Handling Edge Cases

**Hardware Failures**: When specific nodes show intermittent failures, cordon off the node and run targeted diagnostics manually, especially given GPU cost  

**Resource Scarcity**: 

- Use branch-based funneling to reduce commits hitting scarce resources
- Collapse multiple commits on feature branches before expensive testing phases
- Allow 1 in 10 builds to proceed regardless to prevent indefinite blocking
